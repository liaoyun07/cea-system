## 为什么没有增配

| 服务 | 平均核数/额度 | CPU限流 | memory.current采样峰/额度 |

| 边缘A | 1.032 / 2 | 0 | 379.52 / 2048MiB |

| 边缘C | 0.852 / 2 | 0 | 181.96 / 2048MiB |

四业务memory.events的max/oom/oom_kill增量均0；采样内存、CPU额度与前后cgroup取证一致。k6全采样窗口平均1.564核、工作集峰2947.82MiB（独立活动窗口约1.89核/7），也无CPU限流。**没有“业务碰到2核/内存额度”的证据，因此未通过增配掩盖连接错误。**

WSL CPU采样峰61.84%、最低可用3305.80MiB、无新增OOM或危急容量保护；但memory full PSI avg10峰11.77%、IO full峰15.75%，期间有130897页换入、165054页换出，不能声称没有宿主内存/IO等待。Windows可用最低2551MiB。未扩大WSL或继续无限增加并发。

错误为14:11:15/14:11:17 UTC，edge-a返回`[Errno 104] Connection reset by peer`，迭代分别34/32。保存的Pod UID一致、重启0、Ready从启动后未变化，事件无Warning，应用日志只有启动记录；没有服务端异常栈或TCP追踪，具体重置源尚未定位，不能归因于Pod重启、额度不足或某个网络参数。

源码已知：边缘计算段`Semaphore(1)`串行；中心融合在全局state.lock内；线程中HTTP转发/返回等待存在。因此CPU额度增加不等于扩大处理并行度。当前证据支持先调查HTTP连接和并行路径，但不证明这些机制之一是唯一瓶颈。本批未修改业务错误恢复、并行度、镜像或自动重试；下一步业务修复超出“按额度增配”需用户确认。
