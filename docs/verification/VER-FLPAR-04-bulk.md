# FLPAR-04 整批取样与阶段诊断

2026-09-15，实验完成，未测出稳定性能收益：各一次预热及三次正式执行共8/8成功；正式平均358.153→362.615MB/s（+1.246%），但平均算法活动时间均为5.638秒，逐组有正有负。未达到2GB/s，不推广为默认实现。源码基线20673447e0d4f7dfe1b018b65878b2a91a85da41；固定FedAvg/CIFAR10/MLP、9客户端、1轮/epoch1/batch1024、评估batch32，不改变数据、模型、采样顺序或计量协议。原生产源码/业务Flow不改，临时配置已恢复。[方案与复测](../../examples/federated/parallel-benchmark/BULK.md)。

## 候选与计量边界

先核对本机cf01-v1镜像的PyTorch2.2.2+cpu源码：`torch/utils/data/_utils/fetch.py::_MapDatasetFetcher.fetch`支持`__getitems__`整批路径；`torch/utils/data/dataset.py::TensorDataset`自身只实现逐项`__getitem__`。候选沿原DataLoader/RandomSampler及其随机数消费，用相同indices执行整批`index_select`后直通，不再逐样本取出/拼接。没有自行复制采样器或改变随机顺序。

原app/model/SDK源码不改；候选镜像只增加`bulk_loader.py`与`bulk_app.py`，train命令改为后者。其余init/aggregate/evaluate继续原cf01-v1镜像。无新生产Java、字段、表、接口、SPI或第二条执行链，不涉及新的Kestra通用能力。

每轮三个原训练分片8333/16667/25000条各处理三次，共150000次真实样本处理、50000条唯一数据。9客户端共153次SGD更新，前后相同；学习率0.01、seed13、模型和评估数据10000条相同。输入、校验、优化器建立、完整训练和写出仍在原SDK区间内，不加预处理、不乘epoch/batch、不将内存中张量容量另计一遍。

CEA为同一16逻辑CPU/约15.39GiB Docker单宿主，服务CPU/内存限制不改；两方式共用临时Worker14/边缘槽4/cloud2、Loop并发上限9。各一次预热r0后正式AB、BA、AB三组；不清缓存，所有尝试保留，只对r1–r3求速率算术平均。不能拿上一批FLPAR-03的484.3MB/s均值代替本批重测基线。

配对速率变化为+10.696%、+4.181%、−11.639%。平均活动时间只减少0.00128%；三次总字节除以三次活动时间之和分别358.004/358.009MB/s，几乎相同。速率算术平均的+1.246%不等于平均耗时降低1.246%，不能据此宣称有效加速。样本少且单宿主有明显波动，没有统计显著性或稳定收益结论；候选第三次更慢的具体原因未通过硬件profiling定位。

每次输入2001085236B、输出17385829B、合计2018471065B（2.018GB），其中完整训练数据文件1848014133B，前后严格相同。全部正式执行accuracy=0.2124、loss=2.2279879444122312；两次预热也一致。该准确率仅说明数学结果保持，不是模型训练质量达标。

预热不计入上表：原方式513.732MB/s、整批362.632MB/s。原方式本批正式均值低于FLPAR-03的484.335MB/s；使用当次交错重测对照，既不挑旧基线，也不拿预热最高值代替正式结果。未采集完整物理CPU/带宽/后台负载轨迹，不把差异定性为某个硬件瓶颈或代码退化。
