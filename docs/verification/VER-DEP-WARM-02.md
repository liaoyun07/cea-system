# VER-DEP-WARM-02 Grafana 扩容效率对照

2026-10-16，**完成**：20条正式计时、2条补测、备用资源采样及清理/环境审计通过。源码基于 `714ba2616e3a922d12f55741fe621539edd71ae3` 加本验证记录同批提交的实验脚本；不涉及平台Java/前端/数据库修改。

方案：[Grafana扩容对照](../../deploy/agent-sandbox/SCALE-BENCHMARK.md)。中心云、同镜像和单Pod资源，普通Deployment与2备用实例池各10次交错1→3；补测空池和库存不足。使用集群内同一monotonic计时器，以新增实例全部Ready、Service就绪端点及逐实例HTTP服务响应为终点。初建/补池/备用开销另计，不把准备成本说成不存在。

## 环境与控制条件

- 中心云K3s `v1.30.6+k3s1`，Agent Sandbox `v1.0.2`，Docker Desktop共享宿主；新Namespace `cea-warm-scale-20261016`。
- Grafana `13.2.4`，镜像digest `sha256:dbbc38ea21103cefb50396340cd88afec779c7e070b0a7bf5a75b4ce46651d3f`。两组镜像均已缓存；全部正式目标Pod的镜像事件均为already present。
- 单实例requests `100m / 128Mi`，limits `1 CPU / 1Gi`，同配置、securityContext、挂载和1秒周期HTTP readiness probe。镜像默认启动，不增加人工启动等待。
- 普通组修改Deployment副本1→3；预热组保留1个业务实例，领取2个Ready的Sandbox，接入同一Service，控制器同时自动补池。10对交错顺序：奇数对普通→预热，偶数对预热→普通；两组均静置10秒后计时。
- `time.monotonic()`在集群内同一个实验程序计时，包含提交API、容器/应用就绪、Service端点和实际转发生效。HTTP响应头携带Pod名称，逐个核验新实例实际通过Service响应，不能由原有实例代答算成功。
- 10次预热均确认两个领取实例的Pod UID、containerID、startedAt、imageID不变；20条正式样本的新增容器均无重启，HTTP验证无错误。两组实际Pod镜像、资源、环境和探针一致。
- Grafana使用独立emptyDir中的空SQLite，不写业务数据；这验证HTTP服务启动和接入，不是多副本Grafana共享数据库/HA或业务吞吐压测。

新增数均为2，因此按冻结口径：

- 扩容可服务耗时降低：`(1 − 0.565843108 / 14.368857871) × 100% = 96.0620%`。
- 效率定义为新增可服务实例数/扩容耗时，效率提升：`(14.368857871 / 0.565843108 − 1) × 100% = 2439.3714%`，新效率约为原来的25.394倍。
- 本批10对均超过效率提高20%的目标：各对耗时降低88.3841%～98.8857%，效率提高760.8857%～8874.2752%。这是**池库存充足时的扩容响应效率**证据；不是从突发业务负载出现起的HPA检测/决策到服务SLO恢复全过程，也不是计算量/总资源开销降低。

| 场景 | 可用业务实例变化 | 请求前备用 | 复用原备用 | 全部新增实例可服务耗时 |
| --- | --- | ---: | ---: | ---: |
| 同Claim链路、空池新建 | 1→3 | 0 | 0 | 14.664179秒 |
| 请求超过库存 | 1→5 | 2 | 2 | 20.850568秒 |

空池必须真实创建/启动Grafana；超库存必须等额外新实例。两次都成功，但没有亚秒级全部扩容完成，不能把库存充足场景外推为任何扩容规模都同样快。

## 准备和后台补池

正式预热组的2个备用实例初建平均13.299569秒（10.672358～15.742163）；扩容请求到库存恢复为2个Ready备用实例平均17.090116秒（13.960799～25.054793）。这些均不等于0，也没有人为停止补池来让领取计时变快。

另建1个原实例＋2个备用实例，两个备用Ready后等待30秒，每隔15秒取一次Metrics API（仅统计两个备用，不含原业务实例）。三个完整采样如下：

| 采样 | 两个备用合计CPU核占用 | 两个备用合计working-set内存 |
| --- | ---: | ---: |
| 1 | 0.022289核 | 590.887 MiB |
| 2 | 0.019740核 | 567.352 MiB |
| 3 | 0.018045核 | 575.602 MiB |
| 三次采样算术均值 | **0.020025核** | **577.947 MiB** |

原始CPU窗口约11.105～17.784秒，两个Pod的采集时刻有数秒错位，timestamp/window均保留；这是短时空闲备用成本观察，不是整批内存积分、启动峰值或长期稳态均值。备用资源requests合计0.2核/256Mi，limits合计2核/2Gi；limits是上限，不是实际占用。另记控制器在清理后单次采样为1m CPU、85Mi内存，不混入Grafana两个备用的数字。

预热的含义是提前支付启动和常驻成本，以换取收到扩容请求后的更短等待。池补充尚未完成时连续扩容可能退回冷启动；不能据此声称所有时段、所有镜像/负载都获得同样比例。
