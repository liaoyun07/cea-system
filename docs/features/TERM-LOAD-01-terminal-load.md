# TERM-LOAD-01 终端负载与调度

2026-10-13：核心功能已实现并发布到 CEA。页面入口为“基础资源管理 → 终端设备接入”，保留设备登记/编辑，新增“负载与调度”。

## 当前能力

1. 脚本创建独立模拟终端及专用执行环境，页面显示所属网关、CPU/内存额度及实际利用率。
2. 选择终端、任务规模、平均到达间隔与随机种子，开始/停止随机开放式请求；无需在页面创建容器。
3. 发送过程中切换“全部终端执行 / DQN 智能卸载”。每个请求冻结其接收时的策略和流程修订，继续复用原 Execution、Worker、Runner。
4. 显示 CPU/内存趋势、成功请求逐个耗时和当前区间累计耗时、异常及待完成数量；按策略显示实际终端/边缘云/中心云执行比例。
5. 保存历史负载记录，可按终端与时间区间查看。停止后等待原执行真正结束再释放终端。

## 职责与边界

模拟的是终端数量、额度、信号和请求到达；应用计算、资源采样、文件传输、任务执行与计时是真实的。终端 Agent 与任务容器共用该终端父 cgroup；共享 DinD/网关和宿主内核不摊入单终端。网关仅负责接入与转发，不创建/管理 Docker。

原始文件最初只在终端，卸载到云/边才上传；计算采用同一个 `offload-signal/off02-v1`。每个已接收请求产生一条原生执行记录，没有另一套任务状态机或新的通用工作流语义。与 Kestra 的差异属于终端业务侧的负载控制/统计，不涉及新增 Executor、Queue 或执行生命周期。

新增 4 个生产 Java 文件（见[文件索引](../01-code-architecture.md)）、V33 的 4 张 edge 自有表及终端最新测量/占用列。跨模块仅通过公开服务组合。API、调用链和计算公式以[接口文档](../contracts/terminal-load.md)为准。

## 验证与未实现部分

291 项 Java、62 项前端单测、86 项浏览器回归、17 项终端及 21 项网关 Python 测试通过。实际 4 终端混合负载的 23 个已接收请求全部成功，另有停止边界 1 次拒绝；加上 8 次云/边校准，31 次执行输出与独立参考一致。详见[验证记录](../verification/VER-TERM-LOAD-01.md)。

脚本支持配置 1～64 个终端，本批只实测 4 个。没有自动训练/替换 DQN、模拟能耗、终端离线恢复或改变旧请求链路；本批是功能联调，不是固定相同轨迹的完整策略配对实验，未证明 CPU/内存降低 25% 或时延降低 40%。计量不等于物理终端整机资源。
